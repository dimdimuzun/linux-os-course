# Модуль 8. Процеси

## 1. Навчальні цілі

Після опрацювання модуля студент повинен уміти:

- розрізняти програму й процес та пояснювати поняття PID, PPID, власника процесу й дерева процесів;
- переглядати процеси за допомогою `ps`, `pgrep`, `pstree`, `top` та інтерпретувати їхнє виведення;
- пояснювати стани процесів (`R`, `S`, `D`, `T`, `Z`) і розпізнавати «зомбі»;
- оцінювати навантаження системи за `uptime`, `top` і `free`;
- керувати фоновими завданнями оболонки: `&`, `jobs`, `fg`, `bg`, `Ctrl+Z`, `nohup`;
- надсилати сигнали процесам командами `kill`, `pkill`, `killall` та пояснювати різницю між `SIGTERM` і `SIGKILL`;
- розуміти, хто має право надсилати сигнали процесам;
- змінювати пріоритет процесів за допомогою `nice` і `renice`;
- виконувати первинну діагностику проблем із процесами: високе навантаження, завислі процеси, «зомбі»;
- застосовувати безпечний підхід до завершення процесів.

## 2. Вступ

Коли ви запускаєте команду, програма з диска завантажується в пам'ять і починає виконуватися. Цей запущений екземпляр називається **процесом**. Linux одночасно виконує сотні процесів: оболонку, термінал, службові програми, мережеві служби, запущені вами команди. Керування процесами — одна з головних адміністративних навичок: треба вміти побачити, що працює, знайти причину повільної роботи, завершити завислу програму й не зашкодити системі.

Матеріал спирається на попередні модулі: оболонка й коди завершення (модуль 4), файлова система `/proc` (модуль 3), права доступу (модуль 6) та користувачі (модуль 7). Кожен процес виконується від імені певного користувача, і саме це визначає, що він може робити і чи можна ним керувати.

Усі вправи цього модуля використовують безпечні команди (`sleep`, `yes`) і виконуються в навчальній Ubuntu 24.04 VM. Приклади виведення є умовними: у вашому середовищі результати можуть відрізнятися.

## 3. Основні поняття

### 3.1. Програма й процес

- **Програма** — файл на диску з кодом (наприклад, `/usr/bin/sleep`).
- **Процес** — запущений екземпляр програми з власною пам'яттю, відкритими файлами, поточним каталогом, змінними середовища й станом.

Одну й ту саму програму можна запустити кілька разів: кожен запуск — окремий процес зі своїм ідентифікатором.

### 3.2. Ідентифікатори й атрибути

Кожен процес має:

| Атрибут | Значення |
|---|---|
| **PID** | Унікальний числовий ідентифікатор процесу |
| **PPID** | PID батьківського процесу, який його створив |
| **UID / користувач** | Від імені кого виконується процес, звідси права доступу (модулі 6–7) |
| **GID, додаткові групи** | Групи, права яких має процес |
| **Стан** | `running`, `sleeping`, `stopped` тощо |
| **Поточний каталог** | Від якого відраховуються відносні шляхи (модуль 3) |
| **Змінні середовища** | Успадковані від батька; експортовані змінні (модуль 4) |
| **Код завершення** | Число, яке процес повертає батьку, коли завершується (модуль 4) |

У оболонці Bash доступні спеціальні змінні:

```bash
echo "$$"
echo "$PPID"
```

- `$$` — PID поточної оболонки;
- `$PPID` — PID її батька;
- `$!` — PID останнього запущеного у фоні процесу.

### 3.3. Створення процесів і дерево

Нові процеси створюються так: батьківський процес створює свою копію (`fork`), а копія замінює свій код новою програмою (`exec`). Тому процеси утворюють **дерево**. Коренем є процес із PID `1` (у сучасних дистрибутивах — `systemd`, див. модуль 10), який запускається першим і породжує решту.

Ланцюжок для команди, яку ви запустили в терміналі, виглядає приблизно так:

```text
systemd (PID 1)
└── ...
    └── gnome-terminal
        └── bash
            └── sleep 100
```

Дочірній процес успадковує від батька змінні середовища, поточний каталог і права користувача, але не змінює їх у батька. Тому `cd` і присвоєння змінних у дочірньому процесі не впливають на оболонку (модуль 4).

### 3.4. Каталог `/proc`

Інформацію про процеси ядро надає у віртуальній файловій системі `/proc` (модуль 3). Для кожного процесу існує каталог `/proc/PID`:

```bash
ls /proc/$$
readlink /proc/$$/exe
ls -l /proc/$$/cwd
head -n 8 /proc/$$/status
ls -l /proc/$$/fd
```

| Запис | Що містить |
|---|---|
| `status` | Ім'я, стан, PID, PPID, UID, використання пам'яті |
| `exe` | Посилання на виконуваний файл |
| `cwd` | Посилання на поточний каталог |
| `fd/` | Відкриті файли й потоки (0 — stdin, 1 — stdout, 2 — stderr) |
| `cmdline` | Командний рядок запуску |

Команди `ps` і `top` читають саме ці дані.

## 4. Перегляд процесів

### 4.1. `ps`

Без параметрів `ps` показує лише процеси поточного термінала:

```bash
ps
ps -f
```

```text
    PID TTY          TIME CMD
   2145 pts/0    00:00:00 bash
   2310 pts/0    00:00:00 ps
```

Для перегляду всіх процесів системи застосовують два поширені формати:

```bash
ps aux
ps -ef
ps -ef --forest
```

| Формат | Стовпці |
|---|---|
| `ps aux` | `USER PID %CPU %MEM VSZ RSS TTY STAT START TIME COMMAND` |
| `ps -ef` | `UID PID PPID C STIME TTY TIME CMD` |
| `--forest` | Показує дерево процесів відступами |

Приклад `ps aux`:

```text
USER   PID %CPU %MEM    VSZ   RSS TTY   STAT START  TIME COMMAND
root     1  0.0  0.3 168892 12816 ?     Ss   09:00  0:03 /sbin/init
student 2145 0.0 0.1  10692  5120 pts/0 Ss   10:15  0:00 -bash
student 2512 0.0 0.0  11884  3840 pts/0 R+   10:30  0:00 ps aux
```

Пояснення стовпців:

- `%CPU` і `%MEM` — частка використання процесора та пам'яті;
- `VSZ` — обсяг віртуальної пам'яті, `RSS` — обсяг фізичної пам'яті, що фактично використовується;
- `TTY` — термінал, до якого прив'язано процес (`?` означає, що його немає);
- `STAT` — стан (розділ 5);
- `COMMAND` — команда запуску.

Вибір і форматування:

```bash
ps -u student
ps -p $$
ps -p $$ -o pid,ppid,user,stat,ni,comm
ps -eo pid,ppid,user,stat,%cpu,%mem,comm --sort=-%cpu | head -n 5
ps -eo pid,user,comm --sort=-%mem | head -n 5
```

- `-u користувач` — процеси користувача;
- `-p PID` — конкретний процес;
- `-o поля` — власний набір стовпців;
- `--sort=-%cpu` — сортування за зменшенням використання процесора (знак `-`).

### 4.2. `pgrep` і `pidof`

Пошук процесів за іменем:

```bash
pgrep bash
pgrep -l bash
pgrep -a sleep
pgrep -u student -a sleep
pidof bash
```

`pgrep` повертає PID процесів, назви яких відповідають шаблону; `-l` додає ім'я, `-a` — повний командний рядок. Це надійніше, ніж `ps aux | grep ім'я`, бо не вистачає в результаті самого `grep`.

### 4.3. `pstree`

```bash
pstree
pstree -p $$
```

`pstree` показує дерево процесів у наочному вигляді; `-p` додає PID. Програма може бути не встановлена: у такому разі скористайтеся `ps -ef --forest`.

## 5. Стани процесів

Стан показує стовпець `STAT` (у `ps`) або `S` (у `top`):

| Код | Стан | Значення |
|---|---|---|
| `R` | Running | Виконується або готовий до виконання |
| `S` | Sleeping | Очікує події (введення, таймера); його можна перервати |
| `D` | Uninterruptible sleep | Очікує завершення операції введення-виведення; його не можна перервати сигналом |
| `T` | Stopped | Зупинений (`Ctrl+Z`, `SIGSTOP`) |
| `Z` | Zombie | Завершений, але батько ще не зчитав код завершення |
| `I` | Idle | Неактивний потік ядра |

Додаткові символи в `STAT`:

| Символ | Значення |
|---|---|
| `s` | Лідер сеансу |
| `+` | Процес у передньому плані термінала |
| `<` | Підвищений пріоритет |
| `N` | Знижений пріоритет |
| `l` | Багатопотоковий процес |

### 5.1. «Зомбі»

**Зомбі-процес** — процес, який завершив роботу, але запис про нього залишається в таблиці, доки батьківський процес не зчитає його код завершення (виклик `wait`). Такий процес не споживає процесор і пам'ять, але займає PID. У `ps` він має стан `Z` і позначку `<defunct>`.

Зомбі **неможливо «вбити»**: він уже завершений. Усунути його можна, змусивши батька викликати `wait` або завершивши батька, тоді зомбі успадковує `systemd`, який його прибере. Поодинокі короткі зомбі — норма; велика кількість свідчить про помилку в батьківській програмі.

### 5.2. Сироти й стан `D`

- **Процес-сирота** — процес, батько якого завершився; його усиновлює процес `systemd`.
- Стан `D` виникає під час очікування диска чи мережевого сховища. Процес у такому стані не реагує навіть на `SIGKILL`, доки операція не завершиться. Тривале перебування процесів у `D` вказує на проблеми з обладнанням або сховищем.

## 6. Моніторинг навантаження

### 6.1. `top`

```bash
top
top -u student
top -b -n 1 | head -n 15
```

`top` у реальному часі показує навантаження й процеси. Приклад шапки:

```text
top - 10:42:01 up 1:42,  2 users,  load average: 0.35, 0.28, 0.21
Tasks: 214 total,   1 running, 213 sleeping,   0 stopped,   0 zombie
%Cpu(s):  3.2 us,  1.0 sy,  0.0 ni, 95.5 id,  0.2 wa,  0.0 hi,  0.1 si,  0.0 st
MiB Mem :   3945.0 total,   1203.4 free,   1102.8 used,   1639.1 buff/cache
MiB Swap:   2048.0 total,   2048.0 free,      0.0 used.   2565.2 avail Mem

    PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
   2845 student   20   0   13892   3840   3072 R  98.0   0.1   0:15.20 yes
```

Основні елементи:

- `load average` — середня кількість процесів, що виконуються або очікують процесор, за 1, 5 та 15 хвилин;
- `Tasks` — кількість процесів за станами, зокрема `zombie`;
- `%Cpu(s)` — розподіл часу процесора: `us` — користувацькі програми, `sy` — ядро, `ni` — процеси з підвищеним `nice`, `id` — простій, `wa` — очікування введення-виведення;
- `MiB Mem` і `MiB Swap` — використання пам'яті та підкачки; `avail Mem` — скільки реально доступно програмам;
- таблиця процесів: `PR` і `NI` — пріоритет і значення `nice`, `VIRT`, `RES`, `SHR` — пам'ять, `S` — стан.

Гарячі клавіші в `top`:

| Клавіша | Дія |
|---|---|
| `q` | Вийти |
| `h` | Довідка |
| `P`, `M` | Сортувати за процесором / за пам'яттю |
| `1` | Показати окремо кожне ядро процесора |
| `k` | Надіслати сигнал процесу (запитує PID та сигнал) |
| `r` | Змінити `nice` процесу |
| `u` | Фільтр за користувачем |

### 6.2. `uptime`, `free`, `nproc`

```bash
uptime
free -h
nproc
```

- `uptime` — час роботи системи, кількість користувачів і `load average`;
- `free -h` — пам'ять (модуль 1);
- `nproc` — кількість доступних процесорних ядер.

`load average` потрібно порівнювати з кількістю ядер: для системи з 4 ядрами значення близько 4 означає повне завантаження, а 0,5 — мале. Високе значення при низькому використанні процесора часто свідчить про очікування диска (стан `D`).

Програма `htop` — зручніша інтерактивна альтернатива `top`; її встановлення розглядається в модулі 9.

## 7. Фонові процеси й завдання оболонки

### 7.1. Передній і фоновий режими

Звичайна команда виконується в **передньому плані** (foreground): оболонка чекає її завершення й не приймає нових команд. Додавання `&` у кінці запускає команду у **фоновому** режимі:

```bash
sleep 300 &
echo "$!"
jobs
ps -p $!
```

```text
[1] 3401
[1]+  Running                 sleep 300 &
```

Оболонка виводить номер завдання (`[1]`) і PID процесу. Номер завдання діє лише в поточній оболонці й відрізняється від PID.

### 7.2. Керування завданнями

| Команда / клавіші | Дія |
|---|---|
| `jobs` | Показати завдання поточної оболонки |
| `Ctrl+C` | Надіслати `SIGINT`: перервати процес у передньому плані |
| `Ctrl+Z` | Надіслати `SIGTSTP`: зупинити процес у передньому плані |
| `bg %N` | Продовжити зупинене завдання у фоні |
| `fg %N` | Повернути завдання в передній план |
| `kill %N` | Завершити завдання за його номером |

Приклад:

```bash
sleep 200
# натисніть Ctrl+Z
jobs
bg %1
jobs
fg %1
# натисніть Ctrl+C
```

Після `Ctrl+Z` процес переходить у стан `T`, після `bg` — повертається в `S` і працює у фоні.

### 7.3. Фонові процеси та закриття термінала

Коли ви закриваєте термінал, його процеси отримують сигнал `SIGHUP` і зазвичай завершуються. Щоб процес продовжував працювати:

```bash
nohup sleep 120 > /dev/null 2>&1 &
disown
```

- `nohup` запускає команду, ігноруючи `SIGHUP`; без перенаправлення вивід потрапляє у файл `nohup.out`;
- `disown` знімає завдання з контролю оболонки.

Для довготривалих сеансів у віддалених системах краще використовувати `tmux` або `screen`, а для постійних служб — `systemd` (модуль 10).

## 8. Сигнали й завершення процесів

### 8.1. Що таке сигнал

**Сигнал** — повідомлення, яке ядро або інший процес надсилає процесу. Процес може обробити сигнал, ігнорувати його або виконати дію за замовчуванням (наприклад, завершитися). Перелік сигналів:

```bash
kill -l
```

Основні сигнали:

| Номер | Назва | Призначення | Можна перехопити |
|---|---|---|---|
| 1 | `SIGHUP` | Розрив з'єднання; багато служб перечитують конфігурацію | Так |
| 2 | `SIGINT` | Переривання (`Ctrl+C`) | Так |
| 3 | `SIGQUIT` | Завершення з дампом ядра (`Ctrl+\`) | Так |
| 9 | `SIGKILL` | Примусове завершення; процес не може його обробити | **Ні** |
| 15 | `SIGTERM` | Ввічливий запит завершитися (за замовчуванням для `kill`) | Так |
| 18 | `SIGCONT` | Продовжити зупинений процес | Так |
| 19 | `SIGSTOP` | Зупинити процес; його не можна перехопити | **Ні** |
| 20 | `SIGTSTP` | Зупинка з клавіатури (`Ctrl+Z`) | Так |

### 8.2. `kill`, `pkill`, `killall`

Незважаючи на назву, `kill` лише **надсилає сигнал**:

```bash
sleep 600 &
kill $!
sleep 600 &
kill -TERM $!
sleep 600 &
kill -9 $!
sleep 600 &
kill -STOP $!
kill -CONT $!
kill $!
```

| Команда | Дія |
|---|---|
| `kill PID` | Надіслати `SIGTERM` процесу |
| `kill -9 PID` або `kill -KILL PID` | Надіслати `SIGKILL` |
| `kill -STOP PID`, `kill -CONT PID` | Зупинити й продовжити |
| `kill -0 PID` | Нічого не надсилає, лише перевіряє, чи існує процес і чи є право надсилати сигнали |
| `pkill ім'я` | Надіслати сигнал усім процесам із відповідним іменем |
| `pkill -u користувач ім'я` | Те саме лише для процесів користувача |
| `killall ім'я` | Надіслати сигнал усім процесам із точним іменем |

`pkill` та `killall` діють на **всі** збіжні процеси, тому перед використанням перевіряйте список командою `pgrep -a ім'я`.

### 8.3. Правильний порядок завершення

Порядок дій із завислим процесом:

1. Визначте процес і його власника: `ps -p PID -o pid,ppid,user,stat,comm`.
2. Надішліть `SIGTERM`: `kill PID`. Це дає змогу програмі зберегти дані й закрити файли.
3. Зачекайте кілька секунд і перевірте: `ps -p PID`.
4. Якщо процес не завершився, надішліть `SIGKILL`: `kill -9 PID`. Програма не отримає шансу прибрати за собою, тому це крайній засіб.
5. Якщо не допомагає й `SIGKILL`, процес, імовірно, у стані `D` або `Z`; потрібно діагностувати причину (розділ 5).

### 8.4. Хто може надсилати сигнали

- Звичайний користувач може надсилати сигнали **лише своїм процесам**.
- `root` може надсилати сигнали будь-яким процесам.
- Спроба надіслати сигнал чужому процесу завершується помилкою `Operation not permitted`.

Перевірити без побічних дій можна за допомогою нульового сигналу:

```bash
kill -0 1
echo "$?"
```

Для процесу `systemd` (PID 1) команда від звичайного користувача поверне помилку.

**Не надсилайте сигнали PID 1 і невідомим системним процесам.** Завершення ключових процесів може призвести до збою системи.

### 8.5. Код завершення процесу, зупиненого сигналом

Коли процес завершується через сигнал, оболонка повертає код `128 + номер сигналу` (модуль 4):

```bash
sleep 600 &
kill $!
wait $!
echo "$?"
```

Результат — `143` (128 + 15). Для `kill -9` це `137`, для `Ctrl+C` — `130`. Команда `wait` очікує завершення фонового процесу й повертає його код.

## 9. Пріоритети процесів

Планувальник ядра розподіляє час процесора між процесами. Вплинути на розподіл можна за допомогою значення **nice** — від `-20` (найвищий пріоритет) до `19` (найнижчий). За замовчуванням — `0`. Чим більше значення, тим «ввічливіший» процес і тим менше процесорного часу він отримує за конкуренції.

```bash
nice -n 10 yes > /dev/null &
yes > /dev/null &
ps -o pid,ni,pri,%cpu,comm -C yes
renice -n 5 -p PID
pkill yes
```

| Команда | Дія |
|---|---|
| `nice -n N команда` | Запустити команду з указаним значенням `nice` |
| `renice -n N -p PID` | Змінити `nice` запущеного процесу |
| `ps -o ni` | Показати значення `nice` |

Правила:

- звичайний користувач може **лише збільшувати** `nice` (знижувати пріоритет) своїх процесів;
- знижувати `nice` до від'ємних значень і змінювати чужі процеси може лише `root`;
- `nice` впливає лише на конкуренцію за процесор: якщо процесор вільний, процес із високим `nice` усе одно працює повністю.

## 10. Процеси, користувачі та права

Кожен процес працює **від імені користувача** і має його права (модулі 6–7). Це пояснює:

- чому команда `cat /etc/shadow` від звичайного користувача завершується помилкою, а `sudo cat` — ні;
- чому процеси веб-сервера працюють від імені `www-data` з обмеженими правами;
- чому звичайний користувач не може завершити чужий процес.

Процеси, запущені через `sudo -u користувач`, мають права вказаного користувача:

```bash
sudo -u "$USER" sleep 500 &
pgrep -u "$USER" -a sleep
ps -eo user,pid,comm | head -n 5
pkill sleep
```

У цьому прикладі `sudo -u "$USER"` запускає процес від вашого ж імені; з іншим користувачем (модуль 7) процес отримав би його права, і звичайний користувач не зміг би його завершити без `sudo`.

Для програм зі `setuid` (модуль 6) ефективний користувач процесу відрізняється від користувача, що його запустив. Саме тому процес `passwd`, запущений звичайним користувачем, може записати зміни в `/etc/shadow`.

## 11. Діагностика проблем із процесами

| Симптом | Перевірка | Імовірна причина | Дія |
|---|---|---|---|
| Система повільна, процесор зайнятий | `top`, `ps -eo pid,user,%cpu,comm --sort=-%cpu \| head` | Один процес використовує ~100% ядра | З'ясувати призначення; `kill`; за потреби `renice` |
| Закінчується пам'ять | `free -h`, `ps -eo pid,user,%mem,comm --sort=-%mem \| head` | Процес із витоком пам'яті | Завершити процес, перезапустити службу |
| Висока `load average` при низькому процесорі | `top` (стовпці `wa`, стан `D`) | Очікування диска або мережевого сховища | Перевірити диск (`df`, `lsblk`) і журнали |
| Програма «зависла» | `ps -p PID -o stat`, `top` | Очікування, нескінченний цикл, стан `D` | `SIGTERM`, потім `SIGKILL`; для `D` — діагностика пристрою |
| Багато `Z` у `top` | `ps -eo pid,ppid,stat,comm \| grep ' Z'` | Батько не читає код завершення | Виправити або перезапустити батьківську програму |
| Процес зупинений | `ps -o stat`, `jobs` | `Ctrl+Z`, `SIGSTOP` | `fg`, `bg` або `kill -CONT` |
| `Operation not permitted` при `kill` | `ps -o user -p PID` | Процес чужий | Використати відповідного користувача або `sudo` (з розумінням) |

Загальний підхід: **визначити → оцінити → діяти м'яко → перевірити**. Спершу виявляємо, який процес і чий він, потім оцінюємо наслідки його завершення, використовуємо `SIGTERM`, перевіряємо результат і лише потім вдаємося до жорсткіших заходів.

## 12. Типові помилки

1. **Одразу `kill -9`.** Програма не встигає зберегти дані й прибрати тимчасові файли. Спершу `SIGTERM`.
2. **Плутанина між номером завдання й PID.** `kill %1` стосується завдання, `kill 1` — процесу з PID 1.
3. **`pkill` чи `killall` без перевірки.** Команда завершить усі процеси з таким іменем.
4. **Спроба завершити зомбі.** Такий процес уже завершений: потрібно усунути причину в батьківському процесі.
5. **`ps aux | grep ім'я` без урахування самого `grep`.** Зручніше `pgrep -a ім'я`.
6. **Невірне тлумачення `load average`.** Значення потрібно порівнювати з кількістю ядер.
7. **Очікування, що `nice` пришвидшить програму.** Він лише змінює пріоритет за конкуренції.
8. **Закриття термінала з довготривалим завданням.** Процес отримає `SIGHUP`; використовуйте `nohup`, `tmux` або службу `systemd`.
9. **Запуск довгих команд у передньому плані й «зависання» оболонки.** Для переривання використовуйте `Ctrl+C`.
10. **Завершення системних процесів без розуміння їхньої ролі.**

!!! warning "Навчальне середовище"

    У вправах використовуйте лише безпечні команди `sleep` і `yes` і завершуйте їх після вправи. Не надсилайте сигнали процесам, які ви не запускали, не чіпайте системні служби й процес із PID 1. Не запускайте програм, що створюють безліч процесів або вичерпують пам'ять.

## 13. Security Note

!!! danger

    Завершення або зміна пріоритету неправильного процесу може порушити роботу системи чи призвести до втрати даних. Права `root` дозволяють надсилати сигнали будь-яким процесам, тому використовуйте їх з особливою обережністю.

Правила безпечної роботи:

1. Перед `kill`, `pkill` і `killall` перевіряйте процес і його власника.
2. Починайте з `SIGTERM`; `SIGKILL` застосовуйте лише коли м'яке завершення не допомогло.
3. Не використовуйте `sudo kill`, якщо достатньо прав звичайного користувача.
4. Не завершуйте процеси `systemd`, `sshd`, диспетчера входу й інші системні служби, не розуміючи наслідків: можна втратити доступ до системи.
5. Пам'ятайте, що командний рядок процесу видимий іншим користувачам у `ps`: не передавайте паролі й токени як аргументи.
6. Підозрілі процеси (невідомі назви, високе навантаження, мережева активність) досліджуйте через `ps`, `/proc/PID/exe`, `/proc/PID/cwd`, не запускаючи їх повторно.
7. Не змінюйте `nice` системних служб без потреби.
8. Для довготривалих процесів використовуйте механізми, що дозволяють їх контролювати (`systemd`), а не фонові запуски з прихованим виводом.
9. Не використовуйте `nohup` і `disown`, щоб приховувати процеси.

## 14. Практичні вправи

Усі вправи використовують безпечні команди. Після кожної вправи завершуйте створені фонові процеси.

### Вправа 1. Власна оболонка в системі процесів

```bash
echo "$$"
echo "$PPID"
ps -p $$ -o pid,ppid,user,stat,ni,comm
ps -p "$PPID" -o pid,comm
ps -ef --forest | head -n 25
```

Завдання:

1. Запишіть PID і PPID оболонки та ім'я батьківського процесу.
2. Знайдіть оболонку в дереві й визначте її попередників до PID 1.
3. Поясніть, що означає `+` і `s` у `STAT` оболонки.

### Вправа 2. Інформація з `/proc`

```bash
ls /proc/$$
readlink /proc/$$/exe
ls -l /proc/$$/cwd
head -n 8 /proc/$$/status
ls -l /proc/$$/fd
```

Завдання:

1. Знайдіть у `status` ім'я, стан, PID, PPID, UID.
2. Поясніть, куди вказують файлові дескриптори 0, 1 і 2.
3. Змініть поточний каталог (`cd /tmp`) і перевірте, як змінилося `cwd`.

### Вправа 3. Перегляд і сортування

```bash
ps aux | head -n 5
ps -eo pid,ppid,user,stat,%cpu,%mem,comm --sort=-%mem | head -n 6
ps -u "$USER" | wc -l
pgrep -l bash
uptime
nproc
free -h
```

Завдання:

1. Назвіть п'ять процесів, що використовують найбільше пам'яті.
2. Порівняйте `load average` із кількістю ядер і зробіть висновок про навантаження.
3. Скільки процесів належить вашому користувачу?

### Вправа 4. `top`

```bash
top -b -n 1 | head -n 15
top
```

Завдання (в інтерактивному `top`):

1. Натисніть `M` і `P`, переконайтеся, що сортування змінюється.
2. Натисніть `1` і запишіть кількість ядер.
3. Знайдіть кількість процесів у станах `running`, `sleeping`, `zombie`.
4. Вийдіть із `top` клавішею `q`.

### Вправа 5. Фонові завдання

```bash
sleep 300 &
sleep 400 &
jobs
echo "$!"
ps -p $! -o pid,ppid,stat,comm
fg %2
# натисніть Ctrl+Z
jobs
bg %2
jobs
kill %1 %2
jobs
```

Завдання:

1. Поясніть різницю між номером завдання й PID.
2. Запишіть стан процесу після `Ctrl+Z` і після `bg`.

### Вправа 6. Сигнали

```bash
sleep 600 &
pid=$!
ps -p "$pid" -o pid,stat,comm
kill -STOP "$pid"
ps -p "$pid" -o pid,stat,comm
kill -CONT "$pid"
ps -p "$pid" -o pid,stat,comm
kill "$pid"
wait "$pid"
echo "$?"
sleep 600 &
kill -9 $!
wait $!
echo "$?"
kill -0 1
echo "$?"
```

Завдання:

1. Запишіть стани процесу після кожного сигналу.
2. Поясніть коди завершення `143` і `137`.
3. Поясніть результат `kill -0 1` від звичайного користувача.

### Вправа 7. Пріоритети

```bash
nice -n 10 yes > /dev/null &
yes > /dev/null &
ps -o pid,ni,pri,%cpu,comm -C yes
renice -n 15 -p "$(pgrep -n yes)"
renice -n -5 -p "$(pgrep -n yes)"
pkill yes
pgrep yes
```

Завдання:

1. Порівняйте значення `NI` і `%CPU` двох процесів.
2. Поясніть помилку під час спроби встановити від'ємне значення `nice`.
3. Переконайтеся, що після `pkill yes` процесів `yes` не лишилося.
4. Якщо ваша VM має кілька ядер, обидва процеси можуть мати по ~100% `%CPU`: різниця в `nice` проявляється лише за нестачі процесорного часу.

## 18. Ключові висновки

1. Процес — це запущений екземпляр програми з PID, PPID, власником, станом і середовищем; процеси утворюють дерево з коренем PID 1.
2. Інформацію про процеси надає `/proc`; `ps`, `top`, `pgrep`, `pstree` — інструменти її перегляду.
3. Стани `R`, `S`, `D`, `T`, `Z` показують, що робить процес; зомбі вже завершений і потребує усунення причини в батьківського процесу.
4. `load average` потрібно порівнювати з кількістю ядер; стовпець `wa` і стан `D` вказують на очікування диска.
5. Оболонка керує фоновими завданнями через `&`, `jobs`, `fg`, `bg`, `Ctrl+Z`; `nohup`, `tmux` і служби `systemd` потрібні для процесів, що мають пережити закриття термінала.
6. Сигнали керують процесами: `SIGTERM` просить завершитися, `SIGKILL` і `SIGSTOP` не можна перехопити; процес, завершений сигналом, повертає код `128 + номер`.
7. Звичайний користувач керує лише власними процесами; `root` може керувати будь-якими.
8. `nice` змінює пріоритет лише за конкуренції; звичайний користувач може лише збільшувати його значення.
9. Діагностика: визначити, оцінити, діяти м'яко, перевірити; `kill -9` — крайній засіб.
10. Кожен процес має права свого користувача, тому питання процесів нерозривно пов'язані з користувачами, групами й правами доступу.
